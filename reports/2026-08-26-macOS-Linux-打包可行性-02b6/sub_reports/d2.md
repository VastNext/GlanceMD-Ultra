# d2. 跨平台运行时与 API 能力

## 本维度要回答的问题

1. macOS/Linux 分别使用什么 WebView 后端？
2. Linux 的 X11/Wayland 和 GTK 集成有哪些限制？
3. 现有 API 哪些需要平台条件编译或替换？

## 搜索覆盖情况

先以 Wry/Tao/Rfd 平台支持做广度发现，再定向核对 Wry 0.49、自定义协议、Linux 构建示例、Tao 事件和 Rfd 后端。原始核验覆盖 docs.rs 的 crate 文档、Wry 官方仓库 README/示例、Cargo 官方文档及当前 `Cargo.lock`。两轮扩展后关键问题均有一手材料支撑。

## 关键发现

### macOS

- Wry 使用系统 `WKWebView`/WebKit，不需要像 Windows 一样分发 WebView2 Runtime；应用仍依赖目标 macOS 自带 WebKit。
- 标准 `WebViewBuilder::build(&window)` 可用，不应导入 Windows extension traits。
- 当前自定义协议注册名是 `glancemd`，macOS 初始 URL 应使用 `glancemd://localhost/`（或与 handler path 约定一致），不能继续写死 `http://glancemd.localhost/`。
- 文件对话框可继续使用 Rfd。同步对话框在主线程调用符合其 macOS 建议。
- Finder 双击/“打开方式”传入的是应用打开事件，不应只依赖 `std::env::args()`；需处理 Tao `Event::Opened { urls }`，把 `file:` URL 转为路径，并在 WebView ready 之前缓存。
- `.with_devtools(true)` 在当前构建是无条件开启。Wry 文档指出 macOS release 启用 devtools 可能使用私有 API；若未来考虑 App Store 必须关闭。即便仅 GitHub 直发，也建议 release 默认关闭、debug 开启。

### Linux

- 当前 Wry 0.49/Tao 0.33 使用 GTK3 + WebKitGTK 4.1（libsoup3）。Ubuntu/Debian 构建机至少需要 `libgtk-3-dev` 和 `libwebkit2gtk-4.1-dev`；运行时由包依赖或 AppImage 策略保证相应共享库。
- 若只走 `WebViewBuilder::build(&window)`，Wry 文档保证的是 X11。要同时支持 X11 和 Wayland，应使用 Tao 的 GTK container（`default_vbox`）及 `WebViewBuilderExtUnix::build_gtk`。这是首版是否宣称 Wayland 原生支持的关键分叉。
- 初始 URL 同 macOS 使用 `glancemd://localhost/`。handler 内部读取 `request.uri().path()` 的逻辑可以复用，但必须在三平台验证根路径与 local-image query。
- Rfd 默认 XDG Desktop Portal，通常能随 GNOME/KDE 工作；需在包说明或依赖中确保 portal backend/libdbus，并保留 Zenity fallback。它和 Wry 的 GTK/WebKitGTK 是两套不同层次的依赖。
- WebKitGTK 是动态系统组件，Linux 不再具备 README 当前所说的“无运行时依赖”。即便 AppImage 可捆绑许多库，WebKitGTK/图形栈兼容性也需要明确基线和实测，不能简单承诺单文件在所有发行版运行。

### API 适配表

| 当前调用 | Windows | macOS | Linux |
|---|---|---|---|
| `WebViewBuilderExtWindows::with_browser_accelerator_keys(false)` | 保留 | 不编译 | 不编译 |
| `WebViewExtWindows::controller()` + `SetBounds` | 保留现有修复 | 删除，依赖 Wry/Tao 布局 | 删除；GTK 容器负责布局，实测 resize |
| `WebViewBuilder::build(&window)` | 保留 | 保留 | 仅 X11 可作为最小方案；X11+Wayland 用 `build_gtk` |
| 自定义协议 URL `http://glancemd.localhost/` | 保留 | 改 `glancemd://localhost/` | 改 `glancemd://localhost/` |
| Win32 stdin pipe 检测 | 保留 | 用 `std::io::IsTerminal` 或 Unix `isatty` | 同 macOS |
| CLI 文件参数 | 支持 | 仅覆盖终端启动，不覆盖 Finder | `.desktop Exec=... %F` 可传参数 |

## 分析

底层库已经具备跨平台能力，核心困难来自项目直接使用了平台扩展。macOS 路径相对简单，因为 WebKit 是系统框架；Linux 路径更复杂，因为窗口、WebView 和文件对话框都牵涉桌面系统组件。推荐首版直接采用 GTK 容器构建以覆盖 X11/Wayland，而不是先发布“Linux”后才发现 Wayland 用户无法使用；但这必须在 GNOME Wayland、KDE Wayland 和至少一个 X11 环境做实机测试。

不建议在本轮顺便升级到尚未稳定迁移完成的 GTK4/WebKit 6 分支。当前项目锁定组合成熟，先完成平台化更符合最小修改原则；依赖升级可另立任务。

## 对终稿的贡献

提供三平台 WebView 后端、Linux 系统依赖、X11/Wayland 决策、自定义协议和文件打开事件的具体适配矩阵。

## 不确定性与空白

- 研究环境无法在 macOS/Linux 实机编译运行，`build_gtk` 的具体 API 名称应以 Wry 0.49 编译器提示和锁定文档最终确认。
- Wayland 下窗口主动聚焦受 compositor 策略限制，单实例“唤醒并前置”不能保证与 Windows 完全一致。
- WebKitGTK 在不同发行版上的最低版本和 AppImage 捆绑策略需在确定发行基线后实测。
