# d3. 原生打包与可信分发

## 本维度要回答的问题

1. 各平台应产出哪些软件包？
2. 是否适合从 Windows 交叉编译？
3. 签名、公证、图标、文件关联和桌面元数据需要什么？

## 搜索覆盖情况

第一轮比较 Cargo Packager、Apple 分发和 GitHub Runner；第二轮专项核对 Apple Developer ID/公证/Universal Binary、AppImage 兼容原则、Freedesktop 文件关联与 Debian 共享库依赖。原始核验覆盖 Apple、GitHub、Rust、Freedesktop、Debian、AppImage 官方资料及 Cargo Packager 文档。关键链路均有官方支撑。

## 关键发现

### 推荐产物

| 平台 | 首发推荐 | 补充产物 | 说明 |
|---|---|---|---|
| Windows | 继续提供 `GlanceMD.exe` | 后续可加 MSI/NSIS | 不改变当前用户路径 |
| macOS | 签名并公证的 `GlanceMD.dmg`，内含 `GlanceMD.app` | 可附 `.app.zip` | DMG 是 GitHub Release 直发的常见体验；`.app` 才是实际应用 bundle |
| Linux | `GlanceMD.AppImage` + `glancemd_*.deb` | 后续 Pacman/AUR、Flatpak | AppImage 覆盖便携需求，deb 覆盖 Ubuntu/Debian 依赖管理与桌面集成 |

### macOS 打包与发布

- 需要 `.icns` 图标，不能直接用 Windows `.ico`；现有高分辨率 `icon.png` 可作为生成源。
- `.app/Contents/Info.plist` 至少包含 bundle identifier、显示名、版本、可执行文件、图标、应用类别；`.md/.markdown/.txt` 文件关联通过 `CFBundleDocumentTypes` 和适当 UTI/role 声明。
- 必须处理 `Event::Opened` 才能真正读取 Finder 传入文件；仅写关联元数据只会“启动应用但不打开文档”。
- 面向普通用户直发时，应加入 Apple Developer Program，使用 `Developer ID Application` 签名，启用 Hardened Runtime，提交 Apple 公证并 staple ticket。未签名/未公证版本可以作为开发预览，但 Gatekeeper 体验差，不宜标成正式版。
- 应同时提供 Apple Silicon 与 Intel。可选两份架构包，或构建两份 Rust binary 后用 `lipo` 合成 Universal 2 再打一个 DMG。对用户最简洁的是 Universal 2；CI 与体积更敏感时可分发两份。
- 最稳妥的发布链路在 macOS runner 上执行，因为 Xcode、`codesign`、`notarytool`、`stapler` 和 `lipo` 原生可用。理论上的非 macOS 签名工具不应作为首选生产路径。

### Linux 打包与发布

- `.desktop` 至少应包含 `Name=GlanceMD`、`Exec=GlanceMD %F`、`Icon=glancemd`、`Type=Application`、`Categories=Utility;TextEditor;`、`MimeType=text/markdown;text/plain;`。实际默认关联由用户/桌面环境的 `mimeapps.list` 决定，安装包不应强行覆盖用户默认。
- `.deb` 应安装 binary、desktop entry 和标准尺寸图标，并声明由实际链接产生的 GTK/WebKitGTK 等依赖。推荐在目标 Ubuntu LTS 上构建并检查 `ldd`/`dpkg-shlibdeps`。
- AppImage 是“单文件分发格式”，不等于静态、零依赖的程序。应在设定的最老支持基线上构建，谨慎处理 WebKitGTK、GTK 和图形栈库，并至少在目标 Ubuntu LTS、更新 Ubuntu、Fedora/Arch 类各做一次启动与功能测试。
- Linux x86_64 应是首发架构。arm64 可由 GitHub Ubuntu arm runner 构建，但桌面 WebKitGTK/AppImage 工具链覆盖度需要额外验证，适合作为第二阶段。

### 打包工具选择

Cargo Packager 与当前“纯 Rust + 单 binary”项目匹配度较高，配置可以放在 `Packager.toml`，支持所需 `.app/.dmg/.deb/.AppImage`、图标和文件关联，并提供 macOS 签名/公证参数。它比迁移整个 Tauri 框架更小；本项目没有必要为了打包而迁移架构。

仍建议把“构建 binary”和“组装/签名 package”分成 CI 两步：先 `cargo build --release --target ...`，再运行 packager。这样故障定位和产物校验更清楚。

## 分析

“从 Windows 一台机器交叉生成所有包”不是推荐方案。Rust 能交叉编译不代表系统 SDK、原生库、包工具和签名链都适合跨宿主执行。最佳实践是每个平台在原生 GitHub runner 构建：Windows 构建 EXE，macOS 构建/合并/签名/公证 DMG，Ubuntu 构建 deb/AppImage。这样也能顺带运行平台 smoke test。

Linux 的发布承诺必须改写：Windows/macOS 可依赖系统预装 WebView，而 Linux 需要 WebKitGTK 动态组件，包体与兼容性不会继续维持“约 900 KB、无运行时依赖”。这是产品文案和用户预期层面的必要适配。

## 对终稿的贡献

提供软件包矩阵、图标/元数据/文件关联要求、macOS 信任链、Linux 依赖策略和原生 CI 宿主建议。

## 不确定性与空白

- 尚未用 Cargo Packager 对本项目实际生成任何包，字段及生成结果必须用 schema 和实包检查验证。
- Apple 证书、团队账户和公证凭据是否已有未知；缺少时只能发布未签名测试包。
- AppImage 是否适合捆绑当前 WebKitGTK 组合必须通过目标发行版测试决定；若兼容成本过高，可保留 `.deb`，改用 Flatpak 作为更可控的跨发行版格式。
