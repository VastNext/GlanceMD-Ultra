## 关键发现

### 当前公开提交流程

1. 准备一台 fnOS 测试设备并完成手动安装/升级/卸载测试。
2. 从飞牛官网加入任意粉丝微信群。
3. 联系飞牛社区主理人，申请进入“应用中心开发者先锋交流群”。
4. 按工作人员要求提交开发者基础信息。已上架维护者提及个人/企业信息、代表作品和技术栈，但官方公开页未列出固定表单字段。
5. 提交 `.fpk`、Manifest 信息、图标、真实截图及测试材料。
6. 根据审核反馈修改，审核通过后由应用中心发布。

开发者后台正式上线后流程可能转为自助提交；本报告不能提前假定其字段和 SLA。

### 应准备的材料

- 最终、可复现构建的 `.fpk`，建议 GitHub Actions 使用固定 fnpack 版本生成。
- 64×64/256×256 图标和商店展示图。
- 真实运行截图，至少覆盖文件授权、文件打开、编辑/预览、保存和错误提示。
- 应用名称、描述、版本、维护者、开源地址、隐私说明、更新说明、最低系统版本和架构。
- 测试矩阵和结果：安装/升级/卸载、x86；若声明 ARM 则必须 ARM 真机；管理员/普通用户；未授权、只读、可写文件；NAS 登录过期；大文件和并发修改。
- 网络与依赖说明。若采用 Node runtime，需声明 `install_dep_apps=nodejs_v22`；若 Docker，需说明镜像来源、架构、网络拉取和持久卷。

### 不能绕过的外部条件

- 官方明确要求发布前在干净的 fnOS 测试设备安装验证。仅靠 GitHub Actions 生成 FPK 不足以上架。
- 加群、开发者身份认证、商店审核和最终发布需要项目所有者参与，智能体无法代替。
- 公开文档没有审核时长、费用、签名要求、隐私政策固定模板或自动化 API，不能承诺。

## 分析

“能生成 FPK”和“能进官方商店”是两个门槛。前者完全可以在 GitHub Actions 自动化；后者当前仍是人工协作流程，并且真机测试是官方要求。最佳策略是先发布 GitHub Release 的侧载测试 FPK，收集真实 fnOS 用户反馈，再带测试证据进入官方开发者群申请上架。

## 对终稿的贡献

提供当前准入路径、发布材料、外部依赖和“侧载测试→商店审核”的合理顺序。
