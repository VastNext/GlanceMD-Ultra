# d1. 飞牛 OS 平台与应用运行模型

## 本维度要回答的问题

1. 飞牛 OS 基于什么系统和硬件架构？
2. 应用应以本地 GUI、浏览器 Web、宿主服务还是 Docker 运行？
3. 应用如何从飞牛桌面启动并访问 NAS 文件？

## 搜索覆盖情况

## 关键发现

### 系统与架构

- fnOS 是面向 NAS 的 Debian 系 Linux，不是桌面 Linux 发行版。标准使用方式是其他电脑/手机通过浏览器访问飞牛桌面。
- x86_64 是成熟主线。ARM 版已经进入公测，但应用兼容性仍不如 x86；部分 x86 应用明确不可用。
- Manifest 的 `platform` 可声明 `x86`、`arm` 或 `all`。只有包本身不含架构相关二进制时才适合 `all`。

### 应用运行模型

飞牛官方支持三种主要 UI/服务模式：

1. **静态页面 + index.cgi**：适合轻量静态 UI；每次请求启动 CGI，不适合持续编辑和复杂文件 API。
2. **Native 宿主服务 + 统一网关**：服务作为 fnOS 应用用户进程运行，通过 Unix Socket 接入 `/app/{appname}`，可获得 NAS 登录用户上下文；官方 Notepad 案例正是此模式。
3. **Docker Compose 应用**：适合已有容器或多服务依赖，Web UI 通过端口或统一网关访问。

“Native”在飞牛语境中指宿主上的后台进程，不是带 GTK 窗口的本地桌面应用。

### 桌面与文件入口

- `app/ui/config` 注册 Web 入口，`type=iframe` 会在飞牛桌面窗口打开，`type=url` 会用浏览器标签页/外部 Web 视图打开。
- 文件入口可声明 `fileTypes: ["md", ...]`，用户从文件管理器右键打开时，系统在 URL 后追加 `path=/vol.../file.md`。
- 统一网关能复用飞牛访问域名和登录态，并注入 `X-Trim-Userid`、`X-Trim-Isadmin`、`X-Trim-Username`。这是多用户文件编辑的正确身份来源。

## 分析

现有 Linux AppImage 即使能在 Debian 上启动，也依赖显示服务器、GTK 和 WebKitGTK 窗口，而 NAS 通常没有用户可交互的物理桌面会话。它既无法自然出现在远程飞牛桌面，也不能复用 NAS 登录态和文件授权。因此“直接安装 Linux GUI 包”技术上与产品模型均不成立。

GlanceMD 应转化为飞牛 Web 应用：前端仍运行 marked.js/highlight.js/编辑器逻辑；后端作为宿主服务或容器提供受控文件 API；飞牛桌面只负责入口、登录态和文件选择/授权。

## 对终稿的贡献

提供系统基础、x86/ARM边界、三种运行模型和“为什么不能直接复用 AppImage”的判断依据。

## 不确定性与空白

- ARM 应用商店的具体审核覆盖和设备矩阵仍在快速演进。
- 官方文档未承诺所有浏览器/移动端对编辑器快捷键、拖放等行为完全一致，需真机与多端测试。
