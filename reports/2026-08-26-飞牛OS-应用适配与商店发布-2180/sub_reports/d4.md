# d4. GlanceMD 适配路线与工程评估

## 本维度要回答的问题

1. 现有 Wry/GTK 桌面包能否直接用于 NAS？
2. Native Web 与 Docker 路线分别需要改什么？
3. 如何安全读写授权的 Markdown 文件？
4. 哪些前端模块可复用？首版支持哪些架构？

## 搜索覆盖情况

基于 d1-d3 的官方平台证据，对当前 GlanceMD 的 Rust IPC、内嵌前端和文件模型做差距分析；使用官方 Native Notepad/Docker 案例建立可实现基线，并通过真实 `fn-reader` 包验证 Docker 路线。三种路线均评估了体验、权限、架构、包体和上架风险。

## 证据记录

| 材料/来源 | 来源类型 | 关键支撑 | 覆盖问题 | 可信度/限制 |
|---|---|---|---|---|
| 当前 `src/main.rs/ipc.rs/file_ops.rs` | 项目源码 | 现有后端绑定本地窗口、Wry IPC 和本机对话框 | 直接移植差距 | 一手 |
| 当前 `src/frontend/*.js` | 项目源码 | Markdown 渲染、多标签、编辑、主题大多是浏览器 JS | 可复用前端 | 一手 |
| 官方 Native Notepad 案例 | 官方模板 | Node 服务 + 前端 + Socket +网关身份 + package 用户 | 推荐路线可行性 | 高 |
| 官方文件入口与授权 API | 官方规范 | fileTypes/path、用户授权、ACL、路径转换 | 文件安全 | 高 |
| 官方 Docker 案例 | 官方模板 | Compose、多架构镜像、端口/Socket | 备选路线 | 高 |
| `fn-reader` 已上架包 | 实例源码 | Docker Web 服务可进应用中心 | 商店实践 | 高但产品不同 |

## 路线比较

| 路线 | 能否复用现有代码 | x86/ARM | 文件权限 | 包/运维复杂度 | 结论 |
|---|---|---|---|---|---|
| 直接封装 Linux Wry/GTK GUI | Rust核心可编译，UI运行模型不适配 | 需分架构且依赖 GTK/WebKitGTK | 难接飞牛用户登录与授权 | 高，且无可见桌面窗口 | 不采用 |
| Native Web：Node 后端 + 现有前端 | 前端复用高，重写 IPC bridge/文件后端 | JS 包可 `platform=all`，依赖官方 Node runtime | 最容易接统一网关和开放 API | 中，官方有同构案例 | **推荐** |
| Docker Web 服务 | 前端复用高，后端可任意技术 | 多架构镜像后可 `all` | 需把开放 API Socket/授权路径安全映射进容器 | 镜像、Compose、拉取与数据卷更复杂 | 可行备选 |

## 推荐目标架构

### 1. 共享前端核心

保留并模块化：

- `marked.min.js`、`highlight.min.js` 与预览 renderer；
- TabManager、editor、查找、目录、主题、分屏与缩放；
- HTML/CSS 视觉系统。

新增统一 `FileBridge` 接口，使桌面版继续调用 `window.ipc.postMessage`，飞牛版改用 `fetch('/app/glancemd/api/...')`。不能让飞牛分支复制整套前端后独立演进。

### 2. 飞牛 Web 后端

首版建议 Node.js v22 Native 服务，理由是：

- 官方案例和运行时依赖可直接参考；
- JavaScript 包不含架构二进制，Manifest 可 `platform=all`；
- Unix Socket、HTTP、JSON 和 fnOS API 调用成本低；
- 不需要维护 Docker 镜像和镜像仓库。

后端职责：

- 通过统一网关监听 `${TRIM_APPDEST}/app.sock`，所有路由位于 `/app/glancemd`；
- 读取 `X-Trim-Userid` 等可信 Header；
- 从 `TRIM_API_TOKEN` 调用授权与 ACL API；
- 对路径做 canonicalize、拒绝 NUL/`..`/软链逃逸，并确保在授权根内；
- 读写前按当前 UID 检查 readable/writable；
- UTF-8 读取、原子保存（同目录临时文件 + rename）、冲突检测（mtime/内容 hash）；
- 限制文件大小和请求 body，记录审计友好的错误但不泄露系统路径。

### 3. 飞牛前端集成

- `manifest` 声明 `micro_app=true` 和最低 fnOS 版本。
- 引入 `@trimjs/web-app`，在应用内选择并授权目录/文件。
- 主入口 `iframe` 使用统一网关；文件入口声明 `fileTypes: ["md", "markdown", "txt"]` 并可 `noDisplay=true`。
- 处理 URL `path` 参数时只把它交给后端验证，不在前端直接信任。
- 适配宿主主题/语言，快捷键避免浏览器保留组合；离开页面/切换文件保留未保存确认。

## MVP 工程清单

### 必做

- 拆出浏览器可运行的前端 shell 与平台 bridge。
- 新增 Node 后端和 API：授权列表、打开、保存、文件元数据。
- 新增 FPK 目录：Manifest、privilege/resource、ui/config、cmd/main、图标、wizard。
- GitHub Actions 下载固定 `fnpack 1.2.3`，构建 `.fpk` 并作为 prerelease asset。
- x86 fnOS 真机安装测试；虽然包可 `platform=all`，在 ARM 真机通过前商店提交应谨慎声明 ARM。

### 首版应暂缓

- 扫描整个 NAS/全文索引、协作编辑、Git 集成、自动保存、多文件批量替换。
- 复用桌面单实例和窗口状态；这些概念在 Web 应用中无意义。
- Docker 双路线并行维护。

## 验收矩阵

- 管理员和普通用户只能看到自己有权访问的文件。
- 未授权路径、路径穿越、软链越界、只读文件保存均被拒绝。
- 从文件管理器右键打开 `.md`，正确加载 `path` 且通过 ACL。
- 打开/保存中文路径、空格路径、空文件、CRLF/LF 和 UTF-8 中文。
- 两个浏览器同时编辑时，后保存者得到冲突提示而非静默覆盖。
- 服务重启后授权状态可恢复；Token 不落盘；日志无文件内容/Token。
- 安装、启动、停止、升级、卸载与保留数据流程正常。

## 分析

这是“共享渲染核心、重写平台壳和文件服务”的中等规模功能，不是简单打包任务。其价值很清晰：飞牛文件管理器可以把 Markdown 直接交给 GlanceMD，用户在 NAS 登录态内编辑，不需下载到电脑再上传。

Node Native 比 Docker 更贴近官方同构案例，也天然规避 x86/ARM 二进制分包。若未来后端需求增长或依赖复杂，再迁移 Docker；MVP 不应同时承担两种运维模型。

## 对终稿的贡献

提供路线矩阵、推荐架构、模块复用边界、安全清单、MVP 范围和验收标准。

## 不确定性与空白

- 没有 fnOS 真机，无法确认 iframe 对现有复杂 UI、剪贴板、下载和键盘事件的全部行为。
- `@trimjs/web-app` 与开放 API是新能力，最低系统/App 版本需要在实现时按所用方法重新核对。
- ARM 商店发布应以实际 ARM 公测设备测试结果决定，不能仅凭 `platform=all`。
