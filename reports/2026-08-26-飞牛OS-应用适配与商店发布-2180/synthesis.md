# Synthesis

## 原始问题

GlanceMD 能否适配飞牛 OS，并作为正式第三方应用发布到飞牛应用中心；如果可以，应该采用什么产品和技术形态，需要完成哪些工程与平台流程。

## 主线判断

1. **可行，而且飞牛官方现有能力与 Markdown 编辑器高度匹配。** 官方支持 FPK、Web 入口、文件右键打开、用户文件授权、ACL 检查、统一网关与 Native/Docker 应用，应用中心已有成熟第三方生态。
2. **不能直接复用现有 Linux AppImage/GTK GUI。** fnOS 是远程浏览器使用的 NAS 系统，“Native 应用”指后台服务进程，不是本地窗口。正确产品形态是“飞牛桌面中的 Web Markdown 编辑器”。
3. **推荐 Node.js Native 服务 + 共享前端核心 + 统一网关。** 这与官方 Notepad 案例同构，可利用官方 Node v22 runtime，不含架构二进制，理论上可声明 `platform=all`；比 Docker 少一层镜像和运维成本。
4. **文件安全是改造核心，而不是 Markdown 渲染。** 现有前端多数可复用，但必须用飞牛 JS SDK/后端 API完成授权、按当前 UID 检查 ACL、规范化路径、限制授权根、原子保存和并发冲突检测。
5. **能自动生成 FPK，不等于能自动上架商店。** 当前官方开发者后台仍未完全上线，公开流程要求加群、进入开发者先锋群、提交包/素材/测试证据并接受人工审核；官方还明确要求真机测试。

## 证据强弱

- 判断 1：**高**。官方开放平台已公开完整规范和 API；入口文档明确支持 `md` 文件右键打开。
- 判断 2：**高**。官方应用模型、统一网关和实际使用方式均指向 Web UI；NAS 上无可交互桌面窗口是架构事实。
- 判断 3：**高（架构可行性）/中（最终商店体验）**。官方给出几乎同构的 Notepad Native 案例，但 GlanceMD 尚未在真机实现和验证。
- 判断 4：**高**。官方明确应用用户 ACL 与当前用户权限是两层检查，文件路径必须视为不可信输入。
- 判断 5：**高**。官方“上架应用”页面明确当前人工渠道和测试材料；后台首页仍显示 coming soon。

## 跨维度共识

- 飞牛版应作为独立 Web 平台壳，与桌面版共享渲染/编辑模块，不应复制整个前端。
- 统一网关优于独立端口，因为它复用 NAS 登录态、同域授权回调和用户 Header。
- 默认以 package 用户运行，禁止 root 长期服务；用户文件必须显式授权。
- 首版从 x86 真机开始。代码包可设计为 `platform=all`，但 ARM 商店声明必须以 ARM 公测设备测试为前提。
- GitHub Actions 可以自动下载固定 fnpack 版本并发布侧载 FPK，但无法替代真机与官方审核。

## 关键冲突与解释

- **“fnOS 基于 Debian”与“Linux AppImage 可直接用”不等价。** 前者说明二进制 ABI 基础，后者忽略了 NAS 没有桌面会话、远程入口、登录态和文件权限模型。
- **`platform=all` 与“ARM 已支持”不等价。** 全架构声明只说明 FPK 不含架构二进制；Node runtime、系统 API和实际设备仍需测试，ARM 生态目前处于公测阶段。
- **Native 与 Docker 都是官方支持，不代表二者成本相同。** Docker隔离更强但增加镜像、架构、拉取、Compose和 Socket 映射；当前简单文件服务更适合 Native runtime。
- **应用授权了目录与当前用户可访问该文件不是一回事。** 第一层让应用用户获得 ACL；第二层仍需用当前登录 UID 检查业务权限。

## 不确定性与信息缺口

- 已确认一台 x86 fnOS 真机可通过 SSH 管理，Node v22、Docker、appcenter-cli 和手动安装均可用；但尚未安装 GlanceMD 测试 FPK。
- 真机当前版本为 `1.2.0203`，低于文件 ACL API 要求的 `1.2.0401`，且未发现 API Scope Socket；需要先升级系统或为旧版本设计授权降级模式。
- 开发者后台上线时间、实名认证字段、审核 SLA、费用和固定隐私模板未公开。
- ARM 公测应用中心的完整审核与兼容矩阵仍在演进。
- 最低 `os_min_version` 必须在实现时依据实际采用 API 的最高要求确定；当前 ACL API 至少要求系统 1.2.0401。

## 对原始问题的回答

可以改造并有现实上架路径，但这是新增一个“飞牛 Web 版”，不是给现有 Linux GUI 换包格式。用户现有 x86 fnOS 设备可以直接承担真机测试；建议先升级系统，再实现 Node Native FPK MVP、通过 SSH/appcenter-cli 自动安装测试、发布侧载包，最后加入官方开发者先锋群申请上架。ARM 支持作为真机验证后的第二阶段。

## 对终稿的结构建议

- 摘要直接给出可行性与推荐路线。
- 用三路线矩阵解释为何不采用 Linux GUI和为何 Native 优于 Docker。
- 用架构图说明浏览器、统一网关、Node服务、开放 API 和文件系统关系。
- FPK 章节给出目录树和核心字段。
- 工程章节区分可复用前端、需重写 bridge、后端安全职责。
- 最后用“侧载测试→真机门禁→开发者申请→商店审核”路线收束。
