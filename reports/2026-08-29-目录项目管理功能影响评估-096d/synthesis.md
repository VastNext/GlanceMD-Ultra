# 综合判断

## 主线结论

该需求不是架构重写，而是一个边界清晰的新子系统。现有“Rust 提供原生文件能力、JS 管理 tab”架构可以继续使用；目录树点击文件能够直接复用 `open_file → file_opened → TabManager.createTab` 链路。

真正的成本不在“读目录”本身，而在项目树 UI、目录规模控制、路径安全、TOC/split 布局协调和三平台文件管理器差异。

## 推荐方案

- 单项目根。
- Rust 负责选择目录、按节点枚举、路径边界验证和 reveal。
- JS 的独立 `ProjectManager` IIFE 负责树状态，tab 继续负责文件内容。
- 目录懒加载，首版不做文件监听。
- 项目树与 TOC 在左侧面板互斥显示。
- Windows/macOS 选中文件；Linux 打开父目录降级。

## 影响等级

- 架构影响：中等。
- Rust 改动：中等，约 150–300 行加测试。
- 前端改动：中到较高，约 350–700 行 HTML/CSS/JS 加测试。
- 既有编辑/Tab 核心：低影响，主要复用，不需重写。
- 跨平台风险：中等，Linux reveal 语义最高风险。

## 工期

- 可演示 MVP：3–5 工程日。
- 推荐可发布版本：6–9 工程日。
- 加文件操作、监听、搜索、多根工作区后：3–6 周。

## 关键决策

1. 项目树与 TOC 是否互斥。推荐互斥。
2. 是否只展示 Markdown；推荐首版只展示 `.md/.markdown`。
3. 是否持久化最近项目与展开状态；推荐可发布版加入，MVP 可不做。
4. Linux “show in file manager” 接受打开父目录而不选中文件。

## 不确定性

- 网络盘和超大型目录性能必须用真实目录验证。
- macOS 大小写敏感卷与 Linux 暴露现有无条件小写路径比较缺陷，必须同时修复。
- 用户若期望接近 VS Code Explorer 的全部能力，当前工期估算不适用。
